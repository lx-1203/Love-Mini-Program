## 前端单元测试策略

Campus Love 项目前端使用 **Vitest** 作为单元测试框架，配合 **@vue/test-utils** 进行 Vue 组件测试。测试配置位于 `apps/client/vitest.config.ts`，支持 TypeScript 与 Vue SFC 文件的直接导入。

### Vue 组件测试

组件测试聚焦于渲染逻辑、用户交互与状态响应。每个 `.vue` 文件对应一个 `.spec.ts` 测试文件，遵循 AAA（Arrange-Act-Assert）模式：

```typescript
import { describe, it, expect } from 'vitest'
import { mount } from '@vue/test-utils'
import MyComponent from './MyComponent.vue'

describe('MyComponent', () => {
  it('renders correctly', () => {
    const wrapper = mount(MyComponent)
    expect(wrapper.text()).toContain('expected content')
  })
})
```

### Pinia Store 测试

Pinia store 测试采用隔离策略，通过 `createTestingPinia` 创建独立的 store 实例，避免跨测试污染。重点验证：
- state 初始值与重置逻辑
- getters 计算正确性
- actions 异步流程与副作用隔离

### API 服务测试

API 层测试使用 `msw`（Mock Service Worker）拦截网络请求，模拟各种响应场景（成功、失败、超时）。测试用例覆盖：
- 请求参数序列化
- 响应数据转换
- 错误处理与重试机制

## 后端集成测试方案

后端基于 **Spring Boot** 构建，集成测试使用 `@SpringBootTest` 注解加载完整应用上下文，结合 `@Testcontainers` 提供隔离的数据库环境。

### 测试注解体系

| 注解 | 用途 |
|------|------|
| `@SpringBootTest` | 加载完整 Spring 上下文 |
| `@DataJpaTest` | 仅加载 JPA 相关组件 |
| `@WebMvcTest` | 仅加载 Web 层组件 |
| `@MockBean` | 替换指定 Bean 为 Mock 对象 |

### Mock 数据准备

测试数据通过 `@Sql` 注解或 Flyway 迁移脚本注入，确保每次测试前数据库处于已知状态。敏感数据（如用户凭证）使用 `faker` 库生成，避免硬编码。

### 数据库测试策略

采用 **H2 内存数据库** 进行快速单元测试，**PostgreSQL Testcontainers** 进行集成测试，确保 SQL 方言兼容性。每个测试类独立事务，测试结束后自动回滚。

## QA自动化框架演进

本轮 QA 自动化框架发生重大演进，引入严格的身份自验证机制、扩展失败模式识别能力、重构帧级裁决扫描架构，并改进 UI 租赁管理器与队列统计系统。这些变更从根本上修正了虚假覆盖率指标，提升了测试结果的可靠性与可追溯性。

### 身份自验证机制

**apply-plan-additions.mjs** 引入了严格的身份自验证机制，确保取景配方中的每一行都具备可追溯的身份出处。该机制的核心原则是：**没有出处的身份不许写入配方**。

#### 身份回填规则

身份回填模式（`--backfill-identity`）遵循以下硬性条件：

1. **只动 precondition / identity 两个字段**，disposition 判决一律不许改变（保持棘轮只降不升的保护）
2. **只修当前确实不可归因的行** —— 已带结构化身份的行不许被覆盖，防止借回填洗掉别人的判决
3. **每行必须带 identityAuthority** 且指向盘上真实存在的文件（lane 源头、只读复判产物或台账行号）
4. **点名才生效**：`--backfill-identity` 必须配 `--upgrade-only` 逐条点名，禁止整批回填

#### 身份归因判据

身份归因判据复制自 `shoot-frameplan.mjs:232-257` 的 `identityResolutionOf` 函数，判断 precondition 是否说清楚身份：

- 对象形态 + 非空 `.identity` 字段 + 正文不是 `"[object …]"` ⇒ 可归因
- 缺失、裸字符串、数组、`"[object Object]"` 或空 `.identity` ⇒ 不可归因

顶层 `identity` 与 `precondition.identity` 必须同一档，两档冲突时不静默取舍，点名拒写。口径同 `emit-frameplan-additions.mjs:103 IDENTITY_CONFLICT`。

#### 落盘后自证

落盘前建立基线快照，落盘后回读自证三条都要成立：

1. **判决一条都没变**（棘轮只降不升，本模式连降都不许做）
2. **未被点名的行除 precondition/identity/identityBackfill 外逐字节相同**
3. **被点名的行现在过归因判据，且配方里不可归因的总数只减不增**

任何一条不成立即判 FAIL，当场拒绝落盘，避免写坏配方等取景腿去发现。

### 执行分诊系统

**triage-exec-failures.mjs** 是执行轮 FAILED / SKIPPED 行的分诊台（只读，不改任何权威件）。本轮新增了多种失败模式识别能力，能够精确区分不同原因导致的执行失败。

#### 双载体索引机制

分诊系统维护两份载体索引：**冻结构建（dist）** 与 **源码树（src）**。同一条"元素找不到"在四个象限中有完全不同的结论：

| dist | src | 结论 |
|------|-----|------|
| 无 | 无 | 用例文案/选择器本就不属于这个构建（规格噪声或产品确实没有） |
| 无 | 有 | 修复波刚刚补上了它（本轮失败，重建后应复验） |
| 有 | 无 | 修复波把它删了（本轮通过的东西下次会没，必须复验） |
| 有 | 有 | 构建里有却定位不到 → 状态没到 / 时机太早 / 作用域找错 |

只看其中一份就会把"harness 找不到"误报成"产品没有"，或反过来。

#### WS 交互腿归因轴

对于 absent 读数，分诊系统通过两个判据区分"静息态真没有"与"这一腿根本看不见组件内部"：

1. **本语料内的正向对照**：同一个选择器在别的行答过 `present(N)`，或被成功下发过 `tap=`
2. **它活在哪个编译文件里**：就在被测页自己的文件里 ⇒ 页面作用域的 `page.$$()` 够得到；只在 `components/**` 里 ⇒ 与"查询进不到组件作用域"分不开，absent 不可归因

#### 新增失败模式桶

本轮新增以下失败模式分类桶：

- **SKIPPED-tap-target-absent-reststate**：交互按判据下发前，静息态探针答 absent，且有正向对照/在本网页编译文件里 ⇒ 量到的结果就是"静息态没有这个部件"
- **SKIPPED-tap-target-absent-unattributed**：同样是下发前答 absent，但类名只在组件自己的编译文件里、本腿对它从来没有一次 present ⇒ 无法在"静息态确实没有"与"page.$$() 进不到组件作用域"之间归因
- **SKIPPED-tap-probe-no-answer**：交互下发前的元素探针没给答案 ⇒ 通道未就绪，这一行的静息态根本没量到
- **FAILED-open-page-unmeasured**：open_page 重试 N 次仍失败，且零取证（route/evidence/observed 三个皆空）⇒ 通道/窗口状态，不是产品判决
- **FAILED-open-page-measured-defect**：open_page 重试 N 次仍失败，但量到了落点/探针/帧 ⇒ 候选产品级页面缺陷，额外否决门禁
- **SKIPPED-observe-only-slice**：交互型判点落进一个按配置就不下发交互的切片 ⇒ 切片配置所致、非产品失败、也非覆盖结论

#### 词表自核机制

分诊系统内置词表自核：遍历 BUCKET 字典，检查每个桶名是否有归类规则能产出它。若有桶挂了名字但没有规则可达，则判红退出，防止执行器改了原因串而分诊台把它整批算成 unclassified。

### 帧级裁决扫描

**verdict-from-frames.mjs** 将「配方 + 取景结果」合成台账判决。本轮从单一目录扫描扩展为**声明派生集**，支持多源取景结果合并。

#### 三源取景集架构

取景集不再钉死在单个目录上，而是按本轮已经在维护的声明索引派生：

- **源 A**：权威索引 `screenshot-manifest.json` 的 `derivation.corpora[].manifest` —— 由 `rebuild-frozen-manifest.mjs` 逐 corpus 登记"本轮有哪些 corpus、各带哪个 gitSha"
- **源 B**：同目录的 `screenshot-manifest.<label>.json` —— 巡检在 corpus-union 腿之前就把本批帧冻成这一族 subset
- **源 C**：旧的 `uidebt-shoot/shoot-results.json` 原样保留，并排在最后 —— 后给的覆盖先给的，而 corpus manifest 只有 shots[]、没有配方点名的机器判点，让带判点的那份赢

显式给了 `--frames` 就完全用显式的那份，口径不许被背后换掉。

#### 三条铁律

1. **只有当轮真拍出来的帧才能改判**。帧不存在、字节太小、或路径对不上 ⇒ 一律不改，并点名
2. **机器判点没过**（该出现的没出现、不该出现的出现了）⇒ 判 `待修复`，把实测值写进去。这是发现，不是失败
3. **判据只能靠人读帧**（FRAME_ONLY）⇒ 状态仍是"待复验"，但 statusEvidence 里必须有帧路径，这样"欠的是人眼"这件事在账上是看得见的

#### 路由级在场账

巡检帧只带 page/state/route，不带配方行 id，所以进不了行级 byId 映射。系统维护独立的 `routeFrames` 账本，记录每个路由当轮出过的帧数量与来源 corpus。对于没有行级帧但有路由级帧的行，写入补丁注明"巡检帧到了这一页这件事要入账，但不能冒充这一条已复验"。

#### 绿损审查

收紧扫描集后必须核"有没有原本被扫的帧离开扫描集"。前值 = 旧默认那一份（源C）里的行；后值 = 现在 byId 里的同一批 id。派生模式下源C 排在最后 ⇒ 恒等。若有离集的原有取景行或帧路径，立即判红，防止证据静默丢失。

### UI租赁管理器改进

UI 租赁管理器在本轮改进了孤儿锁处理机制，并支持多目录状态扫描。

#### 孤儿锁处理

当取景腿异常退出时，可能留下未释放的 DevTools 租约（孤儿锁）。改进后的租赁管理器在启动时检测孤儿锁，并通过以下策略处理：

- 若租约持有者进程已不存在 ⇒ 强制释放
- 若租约持有者进程仍存在但无响应 ⇒ 超时后强制释放
- 记录释放日志，便于追踪租约泄漏根源

#### 多目录状态扫描

队列统计系统现在支持扫描多个目录的状态，而非仅限于单一输出目录。这使得：

- 不同设备队列的取景结果可以独立存储与统计
- 历史轮次的取景数据不会被新轮次覆盖
- 统计报告可以按目录维度聚合，便于对比不同配置下的测试结果

## 测试覆盖率要求

### 前端覆盖率目标

前端单元测试覆盖率目标为 **80%**，涵盖语句、分支、函数与行覆盖率四个维度。覆盖率报告通过 Vitest 内置的 `--coverage` 标志生成，输出格式为 HTML 与 LCOV。

### 虚假覆盖率指标修正

本轮 QA 自动化框架修正了虚假覆盖率指标问题。**apply-plan-additions.mjs** 的身份自验证机制确保只有真正被执行且具备可追溯身份的取景行才被计入覆盖统计，避免了以下虚假覆盖场景：

- 配方行 precondition 被上游生产者 String() 成 `"[object Object]"` 后身份正文丢失，导致取景门把这些行一律判成不可归因而拒拍，但这些行仍被计入"已覆盖"
- 巡检帧只带 page/state/route、不带配方行 id，也没跑本条的判点，却被当作该条已复验的证据

**verdict-from-frames.mjs** 的路由级在场账明确区分"巡检帧到了这一页"与"该条配方行已复验"，前者只入账不冒充覆盖，后者必须有行级帧与机器判点。

### 真实覆盖验证

**verify-real-coverage.mjs** 通过读取 ops 语料中声明的 `c.automatable === false` 字段，与分诊台的盖章登记册、执行器的拒跑名单使用同一个字段、同一条严格判等。这样三家用的是同一把尺：判据台盖章 ⇒ 执行腿拒跑 ⇒ 覆盖门免检 ⇒ 分诊台认预期，而不是让分诊台只信执行器自报的那句 prose。

## 测试数据管理

### 测试数据生成

测试数据通过以下方式生成与管理：

- **种子脚本**：`database/seed-demo-data.sql` 提供基础演示数据
- **动态生成**：使用 `faker` 库在测试运行时生成随机但符合业务规则的数据
- **数据快照**：关键测试场景的数据状态通过 Flyway 迁移脚本固化，确保可重复性

### 测试环境配置

测试环境通过 Docker Compose 编排，包含：

- PostgreSQL 数据库（集成测试）
- Redis 缓存（会话与队列测试）
- MinIO 对象存储（文件上传测试）
- Nginx 反向代理（HTTPS 与负载均衡测试）

环境变量通过 `.env.test` 文件管理，敏感信息通过 Vault 注入。

## CI/CD集成方案

### GitHub Actions 工作流

项目使用 GitHub Actions 实现自动化测试流水线，主要工作流包括：

1. **PR 验证**：运行单元测试、类型检查、代码规范检查
2. **每日夜间回归**：执行完整的 E2E 测试套件，生成覆盖率报告
3. **发布前验收**：运行性能基准测试与安全扫描

### 测试报告集成

测试结果通过以下方式集成到 CI/CD 流程：

- **JUnit XML**：单元测试与集成测试结果转换为 JUnit 格式，GitHub Actions 原生支持
- **HTML 报告**：E2E 测试生成 Playwright HTML 报告，通过 GitHub Pages 托管
- **覆盖率徽章**：前端覆盖率数据推送到 Codecov，README 显示实时徽章

### 失败重试策略

对于偶发性失败的测试用例，CI 配置了自动重试机制：

- 单元测试：最多重试 2 次，间隔 5 秒
- E2E 测试：最多重试 1 次，间隔 30 秒
- 连续失败 3 次的用例自动标记为 flaky，需人工介入排查

## 性能与兼容性测试

### 性能测试

性能测试使用 **Lighthouse CI** 与自定义脚本结合：

- **Lighthouse CI**：监控核心 Web 指标（FCP、LCP、CLS、TBT）
- **自定义探针**：`scripts/probe-*.cjs` 系列脚本测量特定交互的响应时间
- **基准对比**：每次 PR 合并后与主分支基准对比，性能退化超过 5% 则阻塞合并

### 兼容性测试

兼容性测试覆盖以下维度：

- **浏览器**：Chrome、Firefox、Safari、Edge 最新两个版本
- **设备**：iOS 14+、Android 8+ 主流机型
- **屏幕尺寸**：320px~1920px 多种视口宽度
- **网络条件**：3G、4G、WiFi 不同带宽与延迟组合

### 安全测试

安全测试包括：

- **依赖漏洞扫描**：使用 `npm audit` 与 Snyk 定期扫描
