## P0（先做，否则其余全白做）：同步的输入桶与裁定相反，是一个活地雷

### 实测（全量数过，不是抽样推断）
同一张封面在三棵树里的字节：

| | 包内 | `full-static` | **`assets-images`（sync 的输入桶）** | uploads 服务态 |
|---|---|---|---|---|
| circle-food | 45,594 | 45,594 | **292,002** | 45,594 |
| circle-music | 41,965 | 41,965 | **348,242** | 41,965 |
| circle-sky | 36,383 | 36,383 | **186,949** | 36,383 |

`assets-images` 桶逐件对包内（116 件全量比）：**一致 104 / 不一致 12 / 包内无此件 0**。
那 12 个不是一类问题，必须分开处理：

- **6 张圈子封面 = 真内容差**（桶里是未压缩原图 292K–380K，包内是压缩版 36K–48K）。
- **6 个 SVG = 行尾差**（`heart-gradient.svg` 桶=501 LF / 包内工作树=508 CRLF，其余 5 个同理差 5–7 字节）。
  桶里那份其实**等于 git HEAD**（HEAD 存 LF），差的是工作树被 `core.autocrlf=true` 换成了 CRLF。

第二类的后果比第一类隐蔽：**当前门是 DRIFT=0 的**，因为 uploads 那几件被我 `git checkout` 还原后
也是 CRLF，两边一致所以看不出来。可 `assets-images` 桶里躺着的是 LF ——
**谁跑一次 `sync --apply`，就把 LF 盖进 uploads，门当场报 6 个新漂移。**
而且它是 OS 相关的：同一份仓在 `autocrlf=input` 的 Linux 机器上 checkout 出 LF、
在这台机器上 checkout 出 CRLF，**同一把门会给出不同读数**。
上一发我数出"12 个漂移"又改口"只有 6 个"，根因就是没把这两类分开——这次按全量数写死在这里。

### 方案
把"包内是唯一真源"这条裁定落到 sync 的输入侧与门的口径上，**两件事都要做**：

① **归一输入桶（最小改动，先做）**：把 `assets-images/` 桶里那 12 件按包内重烤
   （6 张封面取压缩版内容、6 个 SVG 取与 uploads 一致的行尾形态）。改动面 12 个文件，不改 sync 语义。

② **门的比对口径按类型分**（这条不做，① 会随下一次包内改动重新烂掉）：
   `verify-app-assets-coverage` 对**文本型素材**（svg）必须先做行尾归一再比 sha256，
   对**二进制素材**（png/jpg/webp/gif）才按字节全等。
   否则这把门的读数绑在 checkout 机器的 `core.autocrlf` 上，换台机器就不是同一个结论——
   这是"可复现"三个字在素材维度上的实际含义。

③ **改输入源为 `full-static`（长期方向，别顺手做）**：语义最自洽，
   但**不是"一行改动"**——`full-static` 是 1345 件整树、`assets-images` 桶只有 116 件，
   换过去等于把 sync 拷贝量放大到 1345 并连带改变 uploads 构成。要做得单独一轮。
   （本条初版被我列成"改动最小"，是错的，已按实测改过排序与措辞。）

### 验证判据（这条比改法更重要）
给 `verify-app-assets-coverage.mjs` 加**三方一致**判点：
cdn 桶每个件必须 `包内 == full-static == uploads == HTTP 响应体` 四值全等，
任一不等点名到 rel。现在的门只比 `包内 vs HTTP`，所以 `assets-images` 桶里那 292,002 的原图
**在门上是隐形的**——这正是它能活过一整轮统一的原因。
配 `--self-test` 阳性对照：造一个只改桶不改包内的场景，门必须能红。

### 需要的授权
纯脚本与门的改动，不写库、不动 uploads。**可直接执行。**

## P1：把审计的视觉真值变成可复现输入

### 实测
`素材/理想效果图/` 19 张 23 MB，`git check-ignore` 确认被 `.gitignore:80` 的 blanket `*.png` 挡住；
R16 的 14 张任务书点名引用其中 **16 张**当整页基准。

两件此前没意识到的事实，让这件事比想象中轻：
1. **LFS 在本仓是真在用的**，`git lfs ls-files` = **6620 个文件**，endpoint 已配好。
   所以"23 MB 进库"不是新风险，是走既有通路。
2. `.gitignore` 早就有**为"这是源不是证据"设计的白名单块**（`!apps/client/src/static/**/*.png`
   等 6 条形态）。`素材/` 属同一类，只是当时没人给它开条。
   ⇒ 我上一轮说"与 `.gitattributes` 裁定相冲"是过悲观了：那条针对 `reports/` 证据帧，
   而本仓对"源素材"的既定解法就是白名单 + LFS。

### 方案（三步，缺一不完整）
① **入库**：`.gitignore` 白名单块加 `!素材/理想效果图/**/*.png`；
   `.gitattributes` 加 `素材/理想效果图/**/*.png filter=lfs diff=lfs merge=lfs -text`。
   只圈这一目录，不放宽任何全局规则。
② **让"缺基准"从静默退化变成响亮失败**（这一步才是真正保住可复现性的）：
   `emit-fidelity-lanes.mjs` 现在遇到基准图不存在，会写"（无基准页：按规范文档 §3 比）"继续出任务书——
   本轮那些"无基准页"泳道就是这么来的。改成：**任务书点名引用的基准图缺失 ⇒ `EMITLANES_RESULT=FAIL` 退 1**，
   并把缺的 rel 逐条点名。判不了就别出卡，别出"降级版"卡。
③ **可核**：把 19 张的 sha256 写进一个跟踪的 manifest（复用 `evidence-store.mjs` 的
   hash16 口径，与 `verify-evidence-corpus.mjs:34` 同一把尺），
   这样即使某台机器只有部分基准图，也能立刻知道手上这张是不是那张。

### 验证判据
- 新机器 `git clone` 后 `git lfs pull`，19 张齐、sha256 与 manifest 全等；
- 故意移走一张 → `emit-fidelity-lanes` 必须 FAIL（这条是自测的阳性对照，不能省）；
- 现有 R16 任务书重出一遍，引用与基准图逐条对得上。

### 需要的授权
① 会往 GitHub LFS 推 23 MB（配额内，但**是共享状态**）→ 需点头。
②③ 纯脚本与新增文件 → **可直接执行**。

## P2：370 条 `*-split` 死注册行

### 实测（全量数过）
全部 823 处 split 引用**都走包内路径**，0 处走 `app-assets`。
`media_asset` 里 `*-split` 行共 **762 条**，分两类：

| 类别 | 条数 | uploads 有件 | 包内有件 | 客户端/后台引用 |
|---|---|---|---|---|
| 纯幽灵 | **370** | 0 | 0 | 0 |
| 有件但无人引用 | **392** | 392 | 392 | 0 |

**更正本文件初版**：初版写"237 条纯幽灵 + 163 条冗余注册"，那是从按 url 排序的**前 400 条抽样**
外推的，不是全量。全量数下来是 370 / 392。教训与 P0 那条同源——split 六族在 url 序上是分块的，
按字母序取前 N 条必然偏向某几族，拿它当比例推整体就是错的。

### 已执行（2026-10-24，用户授权 P2）
只删 370 条纯幽灵。**392 条不删**——它们在 uploads 与包内都真实存在、可被服务，
只是当前没人引用；删一个"活着但暂时没被用"的资产，和删一条"注册了但哪都没有"的幽灵，
不是同一件事，后者才是本项要解决的。

按本仓纪律走完再删：
1. 按**显式 id 列表**定位（不用 `LIKE '%split%'`，否则一梭子会把 392 条有件的也带走）：
   `SELECT id … WHERE url IN (370 条 url)` → 命中 **370** 条，与算出的数逐位相符。
2. `mysqldump --complete-insert` 转储这 370 行（81,855 B，含原 id）→ `database/backup/split-ghosts-<stamp>/`。
3. 写 `ROLLBACK.sql` + `DELETE.sql`。
4. **实跑往返预演**：`1714 → DELETE → 1344 → ROLLBACK → 1714`。可逆性是量出来的。
5. 正式删除：`app_asset` 1714 → **1344**，`*-split` 剩 392（即有件那批），泄漏路径行 0。
6. 复跑资产门：`ASSETCOV_RESULT=PASS 分母=924 200同字节=924 404=0 DRIFT=0`。

### 防复长（已落地）
新增 `scripts/qa/verify-asset-registry.mjs`：注册表 ↔ 磁盘**双向**对账，
`行在件不在` 与 `路径泄漏` 判硬红，`件在行不在` 只报不红（多为刻意 `.bak` 备份与已弃用残留，
判红会逼人删备份，那是更坏的结果）。两个载具已接线（含 `--self-test`），
`GATESYNC_RESULT=PASS 孤儿 3/基线 3`。
自测 5 例，其中一条专门防"路径塌成裸文件名"——我第一版 `walkFiles` 写成
`relative(d,f)`（相对当前子目录而非根），把 1349 个带目录路径塌成 1175 个裸名，
虚报 1342 条 noFile；而**当时的自测照样 5/5 通过**，因为它拿的是根层文件 `default-avatar.png`
当阳性对照，塌不塌都判对。换成"必须有一个带子目录的真件判不缺失"才抓得住这类 bug。

### 需要的授权
**要写库**（DELETE 370 行）。虽可回滚，但属 DB 写 → 需明确点头；P0 没做完之前也别删，
因为 P0 的同步一旦跑，可能又注册回来。
