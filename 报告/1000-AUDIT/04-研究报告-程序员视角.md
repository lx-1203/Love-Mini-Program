## 一、架构评价

### 1.1 三层 monorepo 全景

| 层 | 技术栈 | 规模（R4 定稿口径） | 问题分布（R4） | 评价 |
|---|---|---|---|---|
| apps/client 小程序 | uni-app + Vue3 + TypeScript + Pinia，编译 mp-weixin + H5 | 约 13 万行（实测 131,277 行） | 993 条 + D/U 30 条 | 组件化程度高；i18n 与 design-token 基建完整 |
| apps/client/subpackages | 分包（setup/legal/discover 等） | 计入 client | 55 条 | 分包隔离合理，未进入主包体积 |
| apps/api 后端 | Java 17 + Spring Boot 3.3.1 | 约 2.9 万行；71 controller / 121 service / 81 repo / 77 实体 | 822 条（**全部修复**） | 分层标准，安全面修复彻底 |
| apps/admin 管理端 | Vue3 独立应用 | 约 2.3 万行（实测 24,780 行） | 523 条 + D/U 3 条 | 双后台遗留（admin-legacy）为唯一结构瑕疵 |
| 基础设施 | MySQL 8 + Flyway 127 迁移；Redis/Redisson；RabbitMQ（降级）；bucket4j；resilience4j；actuator/prometheus | `database/flyway/sql/` 130 个 V*.sql | 122 条 | 中间件选型务实，全部为可替换开源件 |

**评价**：monorepo 三层划分符合"小程序 + 服务端 + 运营后台"的典型业务形态；client 与 api 之间以 `docs/openapi` 契约为唯一事实源，admin 与 api 之间亦然，未出现"三端各说各话"的架构漂移。

### 1.2 real/mock 双 profile 设计

`application.yml`（默认）/ `application-real.yml` / `application-mock.yml` 三文件构成双 profile：

- **mock profile**：保留本地演示能力（演示充值 `APP_DEMO_RECHARGE_ENABLED:true`、模拟校园认证 `APP_CAMPUS_CERT_SIMULATE_ENABLED:true`），供离线开发与验收基建（miniprogram-automator）使用；
- **real profile**：演示类开关默认关闭（R4-00312、R4-00358 修复后），密钥/DB 连接全部走 `APP_*` 环境变量注入（`application-real.yml`），`strictAes` 强制生产校验；
- **门禁**：AES 兜底密钥 fail-fast（R4-00246 修复后未配置密钥且非严格模式时拒绝加密写操作），杜绝"配置缺失静默降级"。

**评价**：双 profile 是"演示能力不污染生产"的正确模式。R4 前的主要问题（演示开关默认开启、模拟认证无环境门控、测试账号进生产产物）均已收敛为"默认关闭 + 环境变量显式开启"。

### 1.3 契约体系

- `docs/openapi/` 共 **8 份 YAML**（check-in、feedback-growth-and-auth、likes、notifications、official-accounts、recommendations、users、village），**112 个操作（ops）**；
- client 侧经 `openapi-typescript` 生成类型（`src/services/generated/api-types.ts`）与 `src/services/api.ts` 消费，admin 侧独立契约；
- spectral 规则集（`.spectral.yaml`）纳入 CI 门禁；
- springdoc-openapi 自动生成 OpenAPI 3 + Swagger UI，`docs/openapi` 与代码双写并用 `lint:openapi` 校验。

**评价**：契约先行是本项目质量的核心支点。R4 中契约漂移类问题（R4-00036、R4-00048、R4-00103 等）均以"对齐 openapi 契约"为修复方向，且 6 个已实现端点未收录契约（R4-00197/00198）列为遗留项——契约体系仍欠最后 10%（见第五章）。

### 1.4 分层合理性

- Controller → Service → Repository 标准三层，71 个 controller 未出现"上帝类"（Top 文件问题密度最高的 Java 类为 `RealAuthService.java` 48 条，属认证聚合点，合理）；
- 事务边界：R2 修复事务失效（构造器 new 组件改 Spring Bean 注入），R4 后 `@Transactional` 生效面完整；
- 并发控制：钱包扣费悲观锁 + 幂等键、签到真实扣费 + 流水，资金链路无"先扣后查"竞态残留；
- 降级策略：RabbitMQ 通过 `MessagingFallback` 降级（R4-00303 修复其 discard 日志脱敏），消息投递有 outbox 补偿，MQ 不可用不阻断主链路。

### JaCoCo 阈值基线锚定说明

`apps/api/pom.xml` 的 `jacoco-check`（`verify` 阶段强制门禁）当前阈值为 LINE 0.30 / BRANCH 0.22 / METHOD 0.32 / CLASS 0.54。这是一个**有意的"基线锚定"策略**而非松懈：

1. **先立门禁、再提阈值**：R4 前项目无覆盖率门禁，直接设高阈值（如 0.60）会令所有历史提交无法通过，门禁形同虚设；锚定当前真实覆盖水平，保证"从今天起新代码不得拉低覆盖率"；
2. **渐进提升**：pom.xml 注释明确"Batch3/4 之后按报告 `target/site/jacoco` 逐模块提升阈值"——按模块（而非整体）逐步上调，避免大模块稀释小模块指标；
3. **配套措施**：jacoco exec 文件落 `java.io.tmpdir`（规避中文绝对路径 + 并行构建相互覆盖问题，pom 注释记载），report/check 显式指定同一 dataFile，保证门禁与报告同源。

**评价**：阈值本身偏低（CLASS 0.54 为最高项），反映后端测试覆盖仍集中于核心链路（认证/钱包/解锁），建议下一迭代按模块提升至 LINE 0.45 / BRANCH 0.35 基线（假设目标）。

### 4.2 本地验证链

`package.json` 根脚本 `verify:phase01` 将编译 → 测试 → 契约 → 构建串为单条命令，与 CI 主链同构，保证"本地过 = CI 过"。

### 4.3 中间件与发布基建

- **MySQL 8**：Flyway 127 迁移版本化（`database/flyway/sql/` 130 个 V*.sql 实计）；R4 修复将弱口令种子移出正式迁移链（R4-00364），迁移链不再携带凭据；
- **Redis/Redisson**：会话/分布式锁/限流载体；bucket4j 限流 + resilience4j 熔断；
- **RabbitMQ**：可降级（`MessagingFallback`），outbox 补偿保消息不丢；
- **可观测**：actuator + prometheus 暴露指标，日志经 accesslog 脱敏（R4-00407 修复 query token 泄露）。

**评价**：门禁链从"密钥 → 静态 → 构建 → 单测 → 覆盖率 → 镜像签名"逐层收紧，是全项目技术债下降速度的机制保证；gitleaks 固定版本 + cosign 签名两项在同类项目中属领先配置。
