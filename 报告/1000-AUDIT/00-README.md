## 三、口径说明

1. **一条 = 一个可定位实例**：每条问题必须可定位（文件:行号）、可复现、可修复，同一模式在 N 处出现计 N 条（逐实例），同文件同行的同类问题可合并为一条。禁止模糊条目。
2. **严重度分级**：P0 生产必炸/安全漏洞/商业化链路断裂/资金风险；P1 功能不符合要求/明显缺陷/合规风险；P2 体验问题/潜在隐患；P3 清理项。
3. **维度分级**：H 硬编码 / T 技术债 / B Bug 与隐患 / F 功能完整性 / U UI/UX / D 设计合理性 / S 数据模拟 / D-U 暗色-多端混合维度。
4. **状态口径**：fixed = 代码侧修复完成并通过门禁；partial = 代码侧可验证部分已完成，完整闭环依赖外部材料/外部服务/后端协同/产品决策（见 09）；open 不存在。
5. **批次口径**：batch-1 = P0 安全契约、batch-2 = P1 功能商业、batch-3 = P2 体验、batch-4 = P3 清理（按严重度为主、可执行性为辅预分配）。
6. **数量对账**：原始 2543 条（8+4 路）→ 合并去重 → CI 门禁追加 5 条（R4-PLUS：JaCoCo 阈值失真/spectral 崩溃/eslint 存量/gitleaks 缺失/游离脚本）→ **2548 条**；fixed 2510（98.5%）+ partial 38（1.5%）。
7. **已知数据异常**：R4-FINAL.tsv 中 4 条记录（R4-00005/00080/00085/00145）描述含 `|` 分隔符致批次列位移，已于 `b106130` 说明；不影响条目标识与状态统计。

## 四、如何复核任意条目

1. **取编号**：从 `01-问题清单-全量.md` 或任意视角报告取 R4-XXXXX 编号。
2. **定位**：按编号查 `audit-round3/R4-FINAL.tsv`，取「文件绝对路径 + 行号」。
3. **查状态与批次**：清单第 9/10 列（status / batch），映射到批次 commit：
   - batch-1 → `4c10b34`、batch-2 → `2fc832a`、batch-3 → `8920b8b`、batch-4 → `5388170`
4. **看修复**：`git show <commit> -- <文件路径>` 查看该文件的修复 diff；对应批次汇总见 `06-修复完成清单.md`。
5. **复验门禁**：按 `07-验证记录.md` 第一节重跑对应门禁命令（测试/lint/build 全链路由 `npm run verify:phase01` 串联）。
6. **查排除项**：若状态为 partial，转 `09-遗留排除项.md` 查排除类别、责任人、后续动作与对应 R4 编号。

> 复核示例：R4-00171（钱包扣费客户端定价 P0）→ batch-1 → `git show 4c10b34 -- apps/api/src/main/java/com/campuslove/api/wallet/WalletController.java` → 服务端定价校验。
